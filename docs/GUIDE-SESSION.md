# Dedicated native guide: integration contract

This is an internal support component for Avalokita, the single user-facing app. ShareBus supplies the communication layer; it is not a second consumer app or setup destination. The component is a foundation for Avalokita's natural-language environment help. First-run inventory, a private vault, learned multi-branch routing and actual configuration/repair are separate implementation and acceptance work. Private history-derived evidence belongs in Avalokita's platform user data outside the shared workspace. Observation is not capability proof, usage is not verified success, historical text is not current authority, and local suitability heads do not perform semantic task decomposition.

This contract describes the guide component and its remaining acceptance work. It is not included in published prerelease `v0.1.0-alpha.1`; the next developer wire candidate `0.1.0a2` is private and unpublished. Actual owned-Windows diagnostic continuity and the frozen help UI have scoped evidence below. The goal remains a useful setup and repair assistant; diagnostic replies alone do not complete that goal.

The current R5 technical specification explicitly names Avalokita as the sole user app and ShareBus as internal communication. It prohibits manual token/native-ID searches, per-app slash commands and manual provider registration instructions. Current source also fixes an optional SQLite journal metadata race without weakening private-root/file guards. Its 14-file freeze passed author regression 155 +3 subtests and independent metadata 22/22, specification propagation 24/24 and startup 24/24. This is source/fixture verification after R4, with zero new actual native inputs; the revised policy's actual model response is untested.

## Visible flow

The launcher adds **도움받기** for the folder the user selected with a picker. It opens one support conversation with one composer. The user can ask, for example, “이 작업실이 왜 연결되지 않는지 알려 줘.” Later clicks return to the same conversation and selected messages.

Opening help creates no model input, changes no app configuration and does not start or resume the business room. Support has its own local service, storage and controls, so the business room may remain offline, paused or stopped. Only a submitted help request starts a bounded native turn. Cancelling help affects that help request only.

Do not ask the user to paste a session ID, token, private file path, database or full transcript. Names and folder pickers handle selection. The local browser signs in automatically with a one-use ticket and proof that requests come from the same local page; no manual token entry is needed. Credentials do not appear in the conversation. Uncertain delivery is shown as unknown and is never automatically resent or routed to all participants.

The first guide profile targets **Claude Code 2.1.303**, using the user's existing supported subscription. Codex and Antigravity are not guide providers until an equivalent tool boundary is verified. General bus adapter support is a separate capability. Unsupported selections fail clearly; the app must not silently substitute another provider or create a replacement conversation.

## Existing account and specification

The guide owns a dedicated native CLI conversation and preserves its exact observed identity. This does not promise attachment to an existing Desktop conversation or inheritance of its tools. It reads the bundled version-matched ShareBus specification, current capabilities, repair boundaries and redacted status. It requests no paid API key and copies no business conversation context. The provider's authentication, permission dialogs and usage limits continue to apply.

The private binding includes the canonical selected folder and filesystem identity, immutable support purpose, provider, observed native conversation and specification hash. Concurrent openings must reuse the same binding. A replaced folder, active other owner or stale identity must not be adopted as the old room. The app retains selected messages and input receipts; a crash or missing result after attempted input leads to an unknown state, without replay or cloning.

The native process runs in app-owned support space, outside the business folder. Its initial tool profile exposes only the fixed, argument-free diagnostic MCP method. It does not expose file, shell, browser/computer, ordinary peer messaging or other MCP tools. Model arguments cannot select a different room or provider. Diagnostic authority is bound to the current human help request and remains separate from the app's private operator credential. Tool availability needs an enforced profile, not just a prompt instruction.

Specification updates refresh context while preserving the conversation. They do not preserve a previous turn's execution authority. Diagnostic output contains bounded connection/control labels and counts, without credentials, native identifiers, full paths or transcripts. An offline room does not become connected or unpaused merely because its state is unavailable.

This increment adds an authenticated, signed read-only diagnostic channel to the new broker. An older broker already running without that channel remains unknown or unavailable to the guide: help does not restart or upgrade it, or fall back to sending raw operator credentials. App registration, a recorded verified messaging channel and current app liveness are separate facts; these diagnostics do not verify current desktop liveness, and global stopped state remains unknown. R4 demonstrated same-conversation restart, blind recall and an actual diagnostic-only reply for one owned Windows Claude profile. Setup/repair remains pending.

## Local operations and authority

| Guide step | Current observed scope | Still required |
| --- | --- | --- |
| Explain and inspect | Versioned context, useful actual replies and scoped diagnostics without business-room mutation in R4 | Other supported combinations and integrated packaged-app acceptance |
| Select room/provider | Folder picker; supported Claude guide profile | Other providers need equivalent actual tool-profile proof |
| Continue later | R4 original native conversation resumed after service restart with blind recall and retained-handle cleanup | Other providers/OSes and existing Desktop continuity |
| Prepare connection | Existing guarded configuration preparation remains the foundation | Concrete change preview, baseline hashes and host-required approval/reload steps |
| Apply setup/repair | Not part of the initial read-only tool surface | Narrow action bound to the current human request, guarded backup/application and verification |

Setup/repair remains required follow-up work. A future request such as “Codex가 답을 안 해. 확인하고 고쳐 줘” must first identify the supported repair and current room. Immediately before applying it, the controller rechecks the human request's scope, provider, folder identity, deadline, control epoch and configuration baseline. Existing guarded preparation, comparison and backups should be reused. The model receives a redacted result, never an operator credential.

A peer message, stale instruction, scheduled check or model suggestion cannot create human authority, resume stopped work, enlarge scope or authorize replay. Repair must preserve user edits, pauses, native approvals and private backups. It must not launch a duplicate active conversation, scrape unrelated transcripts, kill an unknown process or retry an uncertain delivery.
